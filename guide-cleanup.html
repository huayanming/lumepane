Cleaning developer caches on macOS without losing anything you need

Every build tool keeps a cache. On a working machine they add up to tens of gigabytes. The rule that makes cleaning safe is narrow, and it is worth stating before any command: delete only what the tool can rebuild from scratch.

The 13 things you can delete without losing data

CategoryPathWhat rebuilding costs
Xcode build cache~/Library/Developer/Xcode/DerivedDataThe next build is a full build
Xcode intermediatesDerivedData/*/Build/Intermediates.noindexSame, but index data survives

Notice what every row has in common: the tool can regenerate it without asking you for anything. That is the whole test.

What looks like a cache and is not

  • ~/Library/Developer/Xcode/Archives — your shipped builds and their dSYMs. Deleting these can cost you the ability to symbolicate a crash report from a version that is already in customers' hands.
  • …/Xcode/iOS DeviceSupport — re-downloaded the next time you connect the device. Safe, but it is the difference between debugging now and debugging after a multi-gigabyte download.
  • …/Xcode/UserData — code snippets, breakpoints, key bindings. Configuration, not cache.
  • ~/Library/Application Support/MobileSync/Backup — local iPhone/iPad backups. This is user data.
  • ~/Library/Containers and ~/Library/Group Containers — application data.
  • Docker or OrbStack volumes — container data, not build output.
  • /Library/Caches — system-wide, needs admin rights, and can break running software.

Doing it by hand

Measure first, delete second:

du -sh ~/Library/Developer/Xcode/DerivedData 2>/dev/null
du -sh ~/Library/Caches/go-build ~/.gradle/caches ~/.npm/_cacache 2>/dev/null

Then remove only what you actually need the space from:

rm -rf ~/Library/Developer/Xcode/DerivedData/*
rm -rf ~/Library/Caches/go-build/*

Two cautions nobody mentions until they bite: quit Xcode before removing DerivedData (a running build will keep writing into it), and never delete a cache while its tool is running.

Why Neeson & Sea quarantine before Neeson & Sea delete

A cache is safe to delete in principle. The interesting failures are the ones where the rule is slightly wrong for your setup: a project pinned to an old cache, a tool that keeps state in there, an archive you had forgotten was an archive.

So the app never deletes on the first pass. It measures, moves the payload into a quarantine folder, and starts a 30-day clock. If something breaks inside that window, one click restores it. Permanent deletion happens only after the window, is off by default, and requires six conditions to hold at once — fail any one and it aborts.

What to expect

For an actively used iOS project, DerivedData is usually the single biggest item (5–50 GB). Node and Rust caches are commonly 1–10 GB each; Gradle and Go a few GB. If your total is under a gigabyte, cleaning is not your disk problem — the Storage panel will show you what actually is.
